# 0.2.8 — 2026-08-30

### Added
- **`# language=<id>` comment injection into heredocs and string literals** — the RubyMine persistent-injection convention now works for Crystal: a whole-line `# language=<id>` comment on the line directly above a heredoc header or string literal injects that language into the body/content, with optional `prefix="…"` / `suffix="…"` attributes (the documented remedy for partial SQL statements). Resolution reuses the marker alias table plus the generic language-ID fallback (`# language=JS` works); a resolvable comment wins over the heredoc marker, an unresolvable one falls back to the marker; `require "…"` paths are excluded. String literals became `PsiLanguageInjectionHost`es: the escaper decodes Crystal escapes so the injected language sees the runtime value and maps offsets back for highlighting, and fragment-editor edits are re-encoded on write-back (interpolated bodies stay no-op). A minimal `CrystalLanguageInjectionSupport` silences the generic IntelliLang comment contributor, making double injections impossible. Covered by `CrystalLanguageCommentParseTest`, `CrystalLanguageCommentInjectionTest`, and `CrystalInjectionHostTest`; specified in docs/specs/heredoc-calls.md.
- **Embedded language highlighting in heredocs (`<<-SQL`, `<<-JAVASCRIPT`, …)** — heredoc bodies whose marker names a language now get that language's syntax highlighting injected via the platform's MultiHostInjector API, mirroring RubyMine's heredoc injection. A curated case-insensitive alias table covers SQL, JS/JAVASCRIPT/ECMASCRIPT, TS/TYPESCRIPT, CSS, HTML, XML, JSON, YAML/YML, MD/MARKDOWN, SH/SHELL/BASH, REGEX/REGEXP, CR/CRYSTAL (self, always available), plus RubyMine-only RUBY and HAML; beyond the table, markers match any installed language ID case-insensitively (e.g. `<<-KOTLIN` in IDEA). Languages that are not installed keep plain string highlighting. Crystal interpolations (`#{…}`) are cut out of the injected fragment with language-specific placeholder prefixes keeping the document syntactically valid, so interpolations keep their Crystal coloring instead of target-language errors. The heredoc literal is now a PsiLanguageInjectionHost with an element manipulator; the annotator skips its enforced body coloring for injected bodies. Covered by `CrystalHeredocInjectionTest` (place layout, aliases, fallback, interpolation splitting) and `CrystalHeredocInjectionMarkerTest`, specified in docs/specs/heredoc-calls.md.
- **Go to Declaration on `require` statements opens the required file** — Ctrl+Click / Ctrl+B on a `require` (keyword or string) previously reported "Cannot find declaration to go to"; navigation to the required file was simply not implemented. The `CrystalGotoDeclarationHandler` now resolves `CrystalRequireStatement` targets through the shared require infrastructure (`CrystalRequireCollector.extractStaticPath` + `CrystalRequirePathResolver`, one compiler-faithful semantics for navigation, completion, and the require graph): relative requires open the file next to the requiring file, non-relative requires search `<project>/lib` and the Crystal stdlib source (shard layouts like `lib/kemal/src/kemal.cr` included), and wildcard requires (`/*`, `/**`) present all matching files as a multi-target popup. Bare directories are not expanded and interpolated/missing paths yield no targets, exactly like the compiler. Stdlib requires open the installed distribution's source files (e.g. `require "json"` → `json.cr`); hovering a require string opens no documentation popup. Covered by `CrystalRequireGotoTest` and documented in docs/specs/require.md.

### Bug Fixes
- **Resolve bare calls through the compiler-imposed base hierarchy (`{error: "…"}.to_json`)** — the valid call was flagged "Missing required argument(s): 'json'" and Go to Definition offered only `NamedTuple#to_json(json : JSON::Builder)`, because no stdlib base type declares its superclass in source: the hierarchy walk stopped at the receiver's own type, so `Object#to_json : String` (the zero-argument overload the real compiler dispatches a bare call to, written inside a reopened `class Object` in `json/to_json.cr`) never entered the overload pool. The method hierarchy now models the compiler-imposed edges — `Int8..Int128`/`UInt8..UInt128` inherit `Int` (there is no abstract `UInt` declaration in the stdlib source; the previous `UInt* → UInt` entries resolved to nothing, while the compiler says `UInt32 < Int`), `Int`/`Float` inherit `Number`, `Number`/`Struct`/`Enum`/`Bool`/`Char`/`Symbol` inherit `Value`, `Value`/`Reference` inherit `Object`, and every class/struct without a declared superclass inherits the compiler base (`Reference`/`Struct`) — so every resolved receiver reaches `Object` (which stays the root, without a self-loop). Bare calls like `{...}.to_json`, `"x".to_json`, and `[1, 2].to_json` now validate against all real overloads and Go to Definition offers the full overload chooser; the implicit base edge degrades gracefully (chainless-but-complete) when the base declarations are absent from the caller's require closure. Covered by `CrystalStdlibObjectHierarchyTest` (real stdlib, Crystal-gated) and new `CrystalMethodHierarchyTest` chain cases; `json/to_json.cr` joined the stdlib parse canary.
- **Restore DOT completion on integer and float literals (`5.<caret>`, `5.5.<caret>`)** — grammar gaps in the real stdlib's `int.cr`/`float.cr` silently dropped `Int32`/`Float64` from stub indexing (while `String` kept working): bare macro invocations with a leading array argument (`Number.expand_div [Int8, UInt8], Float64`), macro-interpolated method receivers (`def {{type.id}}.from_digits`), qualified method names (`def Float64.new`), macro-interpolated local types (`num : {{type.id}} = 0`), and multi-assignments with postfix modifiers (`u, v = v, u if u > v` — the trailing `if` swallowed the enclosing method's `end`). All five forms now parse; the array-argument form requires a trailing comma so bracket index access (`config["envs"]`) keeps binding as index. Completion additionally switched to a lenient method collection — an incomplete hierarchy (macro-generated members in types like `Number`) no longer empties the suggestion list, it offers every explicitly written method; named resolution for diagnostics keeps strict semantics. The implicit primitive hierarchy gained `Float → Number` so Number's methods (`round`, `clamp`) are reachable from float receivers, and leftover v13 debug output was removed. The stdlib parse canary now covers `int.cr`/`float.cr`/`number.cr`/`comparable.cr`, and a new real-stdlib integration test asserts literal completion (`CrystalStdlibLiteralCompletionTest`); parser patterns are pinned by `PrimitiveStdlibParsePatterns`.
- **Fix language injection support registration and stub initialization under module dependencies** — the `CrystalLanguageInjectionSupport` extension was silently excluded because two descriptor details did not match the IntelliLang module's contract: the extension must use the `org.intellij.intelliLang` extension namespace with a plain `<languageSupport/>` tag (the EP's qualified-name prefix `org.intellij.plugins.intelliLang.` does not resolve as an extension namespace — DatabaseTools is the in-product precedent), and the required module is `intellij.platform.langInjection` (artifact name), not the fragment's `org.intellij.intelliLang` value. With the now-loading module dependency, the platform's descriptor loading order deferred the stub element type enumeration past index initialization ("All stub element types should be created before index initialization" regressions in CrystalAnnotatorTest); `CrystalFileType`'s static init now references `CrystalStubElementTypeHolder` so the element type constants exist at file type registration (application start), independent of classloading order. Covered by the silencer contract test in `CrystalLanguageCommentInjectionTest` and the previously failing annotator regressions.
- **Hover on top-level calls shows the real method documentation** — hovering `run` inside `{{ run("…") }}` (or any top-level call without a resolvable definition in the PSI ancestor chain) fell back to the variable rendering "Any (Variable)" because the documentation provider checked the variable case before consulting the PSI reference. Reference resolution now runs first: definition-typed resolutions (methods, classes, modules, structs, enums — builtin macro-methods included) render their real signature, while variable hovers keep the type-inference rendering unchanged. Covered by hover regressions in CrystalMacroContextResolutionTest.
- **Resolve unqualified calls in macro context to macros (`{{ run("…") }}`)** — the type-check inspection flagged the compile-time macro `run(filename, *args)` with "Type mismatch: expected 'Array(String)', got 'String'" because unqualified name lookup bound `Catalyst::CLI.run(Array(String))` (name-based, require-visible). Macro context (`{{ … }}` interpolations and macro bodies) now resolves unqualified names to project macros or builtin `Crystal::Macros` macro-methods only — `compiler/crystal/macros.cr` is indexed as a single-file stdlib root (the compiler tree itself stays excluded), `CrystalReference` prefers macro targets there, and argument-count/type-check inspections suppress ordinary argument diagnostics inside macro context (qualified calls like `Catalyst::CLI.run("str")` keep their diagnostics; backtick method names `def \`(command)\`` and operator names (`<<`, `==`, `[]`, …) now parse, unblocking the whole macros.cr file). Covered by `CrystalMacroContextResolutionTest` (stdlib-gated goto resolution), type-check/arg-count regression tests, and the macros.cr parse canary.

- **Parse heredoc calls inside argument lists — including multiple heredocs (`assert_diff(<<-FIRST, <<-SECOND)`)** — spec files with heredoc arguments were falsely marked ("expected, got 'do'", "Missing required argument(s)") because the lexer folded the call's closing `)` plus any further same-line content into one giant token, making it impossible to represent several heredoc arguments or bind their bodies inside the argument list. The lexer now emits a HEREDOC_START marker token per delimiter and continues the header line as ordinary code; queued bodies open at the following newlines (chained via a preamble state). The grammar treats each header as an ordinary marker argument inside `argument_list` and attaches the string bodies to the owning statement/call_args, so argument counting, splat/named handling, type checking (heredoc ⇒ String) and completion all work through the standard code paths — the former closeless special-casing was deleted entirely. Binding semantics and edge shapes (mixed normal/heredoc args, closer on its own line, terminator-line-only rule) were verified against the real Crystal compiler. Heredoc coloring is now PSI-enforced by the annotator (body=string, delimiters=CRYSTAL_HEREDOC_DELIMITER), so renaming header/terminator delimiters no longer leaves bodies or terminators styled as ordinary code after incremental relexes — no file reopen needed, multi-heredoc chains included; interpolation coloring inside bodies is preserved. Covered by `HeredocClosingParenCalls`, `SpecModulesWithHeredocs`, `GroupedAssignmentParens`, `MultiHeredocBodies` parser tests, argument-count and type-check inspection regressions (multi-heredoc, mismatch highlighting the marker), annotator enforcement tests, and docs/specs/heredoc-calls.md.
- **Parse empty brace blocks after method calls (`Thread.new { }`, `spawn { }`)** — valid empty block bodies were falsely highlighted with "Empty hash literal requires type: use '{} of KeyType => ValueType'" because the grammar required a non-empty statement list in blocks, so a bare `{ }` fell through to the bare-argument alternative and committed as a zero-entry hash literal, starving the trailing `[block]`. Block bodies are now optional for both `{ … }` and `do … end`, and all call forms that take bare arguments plus a trailing block (`method_call_expression`, `dot_call_access`, `macro_interpolation_call`) gained an `!LBRACE` guard so a brace directly after the callee always binds as a block — matching real Crystal, where even `f {"a" => 1}` is rejected as a malformed block. Braces in argument position (parenthesized or after a comma: `f 1, {"a" => 2}`, and its error case `f 1, { }`) remain hash literals. Covered by the new `EmptyBlocks` parser test and new positive/negative inspection cases.
- **Restore Hash default-value constructors (`Hash(String, Int32).new(0)`)** — the valid default-value argument was marked "Too many arguments: expected at most 0, got 1" because `hash.cr` stopped parsing at the nilable compound restriction `(Hash(K, V), K -> V)?`; only the earlier parameterless initializer was indexed, while both later `def self.new` overloads disappeared. Parenthesized, Tuple, and NamedTuple type forms now accept Crystal's `?` suffix, preserving the constructor stubs and resolving `new(0)` to `self.new(default_value : V, initial_capacity = nil)`. The stub version was bumped to rebuild persisted indexes. Covered by a parser golden, a synthetic argument-inspection regression, and a real-stdlib Hash resolution/navigation test.
- **Accept initializer-backed constructor overloads beside explicit `self.new` (`Deque(Int32).new`)** — parameterless `Deque(Int32).new` was incorrectly marked "Missing required argument(s): 'array'" even though it compiles. Crystal adds implicit `new` forwarders for every `initialize` overload and keeps callable-distinct forwarders alongside explicit `def self.new` overloads, but constructor resolution previously selected the explicit `self.new` definition set and discarded every initializer. Resolution, navigation, hover, and argument inspection now share the combined overload pool; explicit `self.new` targets remain first for stable presentation and shadow only initializer forwarders with an overlapping default-expanded dispatch signature, while implicit zero-argument construction is used only when the resulting pool is empty. Covered by synthetic generic-constructor tests, merged polyvariant navigation tests, explicit-shadowing coverage, and a real-stdlib Deque integration test.
- **Resolve constructors in stdlib types that define setters (`URI.new("http", "localhost", 9999)`)** — the arguments were flagged with "Too many arguments: expected at most 0, got 3" and hover on `new` showed only "Any (Variable)". Root cause: the grammar had no setter form for method definitions (`def host=`, `def query_params=`), so real stdlib files like `uri.cr` failed to parse and stub indexing lost members of the surrounding type — including its `initialize`, which made constructor resolution fall back to the zero-argument implicit-constructor rule. Setters now parse (instance, `self.`, and abstract forms), are indexed under their Crystal name `host=`, nested bare calls nest like Crystal (`exec new_request m, p` → `exec(new_request(m, p))`), and macro-interpolated callees accept bare/named arguments and blocks (`{{method.id}} path, form: body`), which unbreaks the generated methods in `http/client.cr`. The file stub version was bumped so persisted indexes rebuild. Covered by new `SetterMethodDefinition` and `MacroInterpolatedCallee` parser tests, a stdlib source parse canary (`CrystalStdlibSourceParseTest`), and constructor argument-count regression tests.
- **Resolve constructors on stdlib types that generate methods through macros (`HTTP::Client.new`)** — hover on `new` still showed "Any (Variable)", Go to definition reported "Can not find declaration to go to", and argument-count checks were silently skipped, although http/client.cr explicitly defines `def self.new(uri, tls)` overloads. Cause: any type containing macro-interpolated method names (`def {{method.id}}` inside `{% for %}` loops) was treated as fully uncertain, suppressing every named lookup against it — including textually written definitions. Macro uncertainty now suppresses only names that are not explicitly defined; a written `def self.new`/`initialize` resolves normally. Covered by new goto-declaration and method-hierarchy tests plus an integration test against the real local Crystal stdlib (skipped when Crystal is not installed).
- **Parse char literals inside string interpolation and macro control blocks** — `"cat-#{rule_id.split('-').last.rjust(3, '0')}"` flagged both `'-'` and `'0'` with "Unterminated char literal" and `<expression> expected, got '''` because the `<INTERPOLATION>` lexer state had no `CHAR_LITERAL` rule. Char literals (including escape forms) now lex correctly in every interpolating literal, the invalid multi-character `'ab'` guard is mirrored from top level, and `macro_control_token` was extended with `CHAR_LITERAL`/`GLOBAL_VAR` so `{% if x == 'a' %}` no longer aborts parsing of the surrounding macro definition. Covered by the new `CharLiteralInterpolation` parser test and four lexer unit tests.
- **Parse assignments in postfix modifier conditions** — `return [] of Result unless target = PAIRS[node.name]?` produced `<…> expected, got '='` because `postfix_modifier` only accepted a plain expression while block-level conditions already allowed assignments. Postfix `if`/`unless`/`while`/`until`/`rescue` now share the block-level `condition_assignment` alternative (flat private rule, no PSI shape change for existing code), and the speculative `in`-clause guard accepts assignments too. Covered by the new `PostfixModifierAssignment` parser test.
- **Parse special global variables inside string interpolation** — `"#{$1}"` (e.g. in regex-replacement blocks like `str.sub(/\.map(...)\s*\.sum/) { ".sum#{$1}" }`) produced `<expression> expected, got '$'` because the `<INTERPOLATION>` lexer state had no `{GLOBAL_VAR}` rule, so `$` fell through to the `BAD_CHARACTER` fallback. `$1`, `$~`, `$?`, and named globals now lex as `GLOBAL_VAR` inside interpolation; the same rule was added to the `<MACRO_INTERPOLATION>` and `<MACRO_CONTROL>` states to keep them mirrored. Covered by the new `GlobalVarInterpolation` parser test across string, regex, command, heredoc, percent-literal, nested-interpolation, and top-level contexts.
